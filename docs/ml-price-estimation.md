# Учебная оценка цены: C++ CLI и необязательная интеграция

Первый этап обучения (`0f44a82`) дополнен необязательной оценкой в подробностях объявления. **Это обучение закономерностям синтетического каталога, не оценка реального рынка Еревана.** Бронирования, цены и генератор не изменены. Сервер только загружает сохранённые модели и вычисляет прогноз; обучение не запускается. Python для обучения/прогнозов не нужен.

## Сборка и запуск

Новые библиотеки не требуются: C++17/STL и уже установленный SQLite. Eigen не нужен. `BUILD_PRICE_ML` по умолчанию **OFF**; обычные команды README сохраняют прежнее поведение.

Для уже сконфигурированной папки:

```sh
cmake -S . -B build -DBUILD_PRICE_ML=ON
cmake --build build -j 4
ctest --test-dir build -R '^price_ml_unit$' --output-on-failure
./build/price_ml --db data/apartments.sqlite3 --out build/ml-price-run
```

Для новой копии сначала установить зависимости из README, затем:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH="$(brew --prefix);$(brew --prefix sqlite)" -DBUILD_TESTING=ON -DBUILD_PRICE_ML=ON
cmake --build build -j 4
# Отдельная учебная база: не использовать эту команду для обновления рабочих данных.
./build/apartment_server --db build/ml-demo.sqlite3 --init-db
./build/price_ml --db build/ml-demo.sqlite3 --out build/ml-price-fresh
ctest --test-dir build -R '^price_ml_unit$' --output-on-failure
```

Это команды macOS/Homebrew, не заявление о проверке другой ОС. Выходной каталог должен быть новым: существующие файлы намеренно не перезаписываются. Для повторения выбрать другое имя, например `build/ml-price-run-2`. Все артефакты в `build/` игнорируются Git. Для отключения необязательной цели: `cmake -S . -B build -DBUILD_PRICE_ML=OFF`.

CLI читает источник одним SELECT через `SQLITE_OPEN_READONLY`, с `query_only=ON`, `foreign_keys=ON` и ожиданием блокировки до 1000 мс. Не создаёт отсутствующую базу, не применяет миграции, не вызывает генератор. Единственный SELECT даёт согласованный снимок исходных строк. При ошибке команда завершается ненулевым кодом; частично созданный каталог результатов нельзя считать законченным экспериментом. Повтор следует запускать в новый каталог.

## Какие строки включаются

Требуется текущая схема с ремонтом (миграция 6). Точный отбор в `ml/read_data.cpp`:

```sql
SELECT p.id, p.area, p.rooms, p.floor, p.kind, p.district, p.renovation,
       l.price, l.deal_type
FROM properties AS p
JOIN listings AS l ON l.property_id = p.id
WHERE p.demo_key = printf('demo-%03d', CAST(substr(p.demo_key, 6) AS INTEGER))
  AND CAST(substr(p.demo_key, 6) AS INTEGER) BETWEEN 1 AND 1000
  AND l.demo_key = p.demo_key
  AND l.seller_user_id IS NULL
  AND l.source_booking_id IS NULL
ORDER BY p.id, l.id;
```

Это первоначальные демопредложения с каноническими ключами `demo-001`…`demo-1000`. Перепродажи и пользовательские объявления исключены. Статус не фильтруется: первоначальное закрытое или забронированное объявление также содержит историческое предложение цены. История пользователей не читается. `demo_revision` не служит условием: сохраняются и защищённые старые демостроки, не обновлённые генератором. Цена — текущая сохранённая цена **исходного** объявления, не цена перепродажи и не `price_at_booking`.

Ключи означают происхождение в рамках приложения, но не доказывают отсутствие ручных правок через DB Browser. Первоначальные значения до таких правок не восстанавливаются. Совпадение `property_id` дважды внутри одной сделки вызывает ошибку вместо случайного выбора строки.

## Разбиение без утечки

Seed **20260914**, до получения метрик. В `splitRows` применяется явно заданный SplitMix64 к `property_id + seed`; остаток по модулю 5 равен 0 — тест, остальные — обучение. Доля около 80/20, а не принудительно ровно 80/20. Один property_id получает ту же часть независимо от типа сделки и порядка чтения. ID — только ключ группировки, **не признак модели**. Выборки сортируются по id для воспроизводимого порядка вычислений; алгоритм не использует зависимый от реализации `std::hash`.

Каждая сделка имеет независимую модель. Средние, масштабы, словари категорий, масштаб целевой цены и медиана вычисляются **только по обучающим строкам**. Тестовая часть используется только для итогового MAE и проверки сериализации. `lambda = 1` зафиксирована заранее; подбора по тесту, перебора seed и выбора лучшего разбиения не было. Повтор эксперимента — проверка воспроизводимости, не дополнительный поиск модели.

## Признаки и формула

Порядок столбцов:

1. Свободный член `intercept = 1`.
2. `area_z`, `rooms_z`, `floor_z`: площадь, комнаты, этаж после стандартизации.
3. One-hot категории `kind` (тип объекта), затем `district` (район), затем `renovation` (ремонт). Для каждого поля — отсортированный словарь обучающих значений и отдельный столбец `<unknown>`.

Для численного признака `z = (x − mean_train) / scale_train`, где scale — стандартное отклонение с делением на N. При постоянном признаке scale принимается равным 1. У категорий ровно один активный столбец на поле. Значение, отсутствующее в обучающем словаре, попадает в unknown; его коэффициент без обучающих примеров получается нулевым благодаря регуляризации. Ремонт `unspecified` — обычная категория, если встречается в обучении. Для домов используется сохранённый этаж, без выдуманных этажей; тип дома кодируется отдельно.

Не используются цена, id, demo_key, описание, адрес или коэффициенты генератора как входные признаки. Цена используется **только как цель обучения**. Генератор не подключён к библиотеке модели; тесты вызывают его лишь для отдельной тестовой базы. Не добавляются взаимодействия площади с районом/ремонтом и полиномиальные признаки.

Чтобы численный масштаб задачи был удобным, целевая цена тоже стандартизируется по обучению:

```text
t_i = (price_i − targetMean) / targetScale
w = argmin [ sum_i (x_i · w − t_i)² + lambda * sum_(j>0) w_j² ]
prediction_AMD = max(1, targetMean + targetScale * (x · w))
```

Свободный член не штрафуется. Сумма ошибок не делится на N; `lambda=1` относится именно к этой формуле. L2 не даёт неустойчивым коэффициентам бесконтрольно расти, в том числе при зависимых one-hot столбцах. Обрезка снизу до 1 AMD явно включена и в оценку, и в загруженную модель; верхнего ограничения нет, это не валидация пользовательской цены.

Решение: к матрице признаков снизу добавляются строки `sqrt(lambda) * I` для всех коэффициентов кроме intercept и нулевые цели. Отражения Хаусхолдера преобразуют задачу в верхнетреугольную систему, далее обратная подстановка. **Обратная матрица и XᵀX не вычисляются.** Это небольшой самостоятельный QR для данной учебной задачи, не замена универсальной численной библиотеки. В тесте проверен независимый аналитический ответ на линейном наборе, а также постоянные/зависимые признаки.

## Реальные результаты

Снимок рабочей базы 14 сентября 2026, схема 6: отобрано 1000 исходных предложений, по 500 каждой сделки. Исторические защищённые демостроки сохранены. Новая полностью сгенерированная база может дать другие метрики: все её объекты будут версии 2 и могут отличаться от рабочей истории.

| Модель | Обучение | Тест | MAE модели, AMD | MAE медианы обучения, AMD | Улучшение |
|---|---:|---:|---:|---:|---:|
| Аренда (за месяц) | 393 | 107 | 48 427,32 | 154 990,65 | 68,75% |
| Продажа (полная цена) | 400 | 100 | 7 577 283,36 | 23 109 000,00 | 67,21% |

MAE — средняя абсолютная ошибка: `sum(abs(prediction − price)) / N_test`. База сравнения всегда выдаёт медиану **обучающих** цен той же сделки. Улучшение: `100 * (MAE_baseline − MAE_model) / MAE_baseline`. Если baseline MAE равен 0, процент не определён; CLI сообщает это. При отсутствии улучшения CLI явно выводит `NO improvement`, тест не требует искусственного выигрыша на произвольных данных.

Фактический запуск:

```sh
./build/price_ml --db data/apartments.sqlite3 --out build/ml-price-final
./build/price_ml --db data/apartments.sqlite3 --out build/ml-price-final-repeat
```

Оба запуска дали одинаковые метрики и побайтно одинаковые файлы. Сравнение логического содержимого всех таблиц до/после подтвердило отсутствие изменений источника.

## Артефакты и загрузка

В каждом каталоге результатов:

- `rent.model`, `sale.model`: текстовый формат `APARTMENT_RIDGE 1`, сделка, seed, lambda, преобразование цели/нижняя граница цены, средние и масштабы, словари категорий, полный порядок признаков и коэффициенты. Числа записываются с `max_digits10`, достаточным для точного восстановления double.
- `evaluation.txt`: версия отчёта, seed и алгоритм разбиения, критерии отбора, размеры частей, MAE, медиана обучения и списки property_id каждой части. Нет email, пользователей, сессий и секретов.

C++ API: `Model::load(path)` и `model.predict(row)`. Артефакт проверяется на версию, порядок/количество признаков, категории, конечность чисел и положительность масштабов; прогноз для чужого типа сделки отклоняется. CLI сразу после сохранения загружает каждый файл и сравнивает прогнозы на всех отобранных строках соответствующей сделки. В реальном прогоне **все 1000 прогнозов совпали точно**, не только в пределах округления. Это проверка сериализации, а не независимая оценка качества: качество оценивается только MAE отложенного теста выше.

Артефакты лежат в игнорируемом `build/`, не в рабочей базе и не в исходниках сервера. Их нужно сохранить отдельно, если требуется воспроизвести именно этот снимок при последующих изменениях каталога. Для использования на сайте каталог нужно явно передать серверу через `--models-dir`.

## Проверки и ограничения

Выполнены сборка CLI и существующего `apartment_server`, `price_ml_unit` (**1/1**), два реальных запуска обучения, сравнение артефактов и содержимого рабочей базы. Проверены отказы для отсутствующей базы и существующего выходного каталога. Тест создаёт собственную временную базу схемы 6 с демоданными и перепродажей, проверяет отбор/чтение без записи, отсутствие пересечения, неизменность разбиения при перестановке строк и смене сделки, воспроизводимость обучения, кодирование/unknown, отсутствие id/цены среди признаков, конечность и сериализацию. Первый прогон выявил недостающий флаг создания базы в тестовой подготовке; он исправлен, последующий прогон успешен. Полный серверный набор не запускался: исходники серверной логики не менялись.

Качество на синтетике **не свидетельствует о качестве на реальных сделках**. Здесь нет реальных рыночных данных, времени экспозиции, инфраструктуры, состояния здания и многих других факторов. Аддитивная линейная модель может существенно ошибаться на больших/дорогих объектах и неизвестных категориях. Метрики — один фиксированный тест, без доверительных интервалов и проверки переноса на другой рынок. Нет выбора лучшей модели по валидации и периодического обучения. Интеграция ниже не изменяет алгоритм, seed, коэффициенты, unknown-категории или исходные метрики.


## Этап 2: загрузка моделей сервером и подробная страница

Минимальное расширение `GET /api/listings/{id}`: `price_estimate` содержит либо `{"status":"unavailable"}`, либо `{"status":"available","amount_amd":123456.75}`. Значение — double из `Model::predict`, без округления API. В UI оно округляется до целого драма и сопровождается периодом «в месяц»/«за объект» и текстом «Модель обучена на синтетических данных каталога. Это не рыночная оценка». Отсутствующее поле старого сервера тоже отображается как недоступность.

`src/price_estimator.cpp` загружает две независимые модели **один раз** до регистрации обработчиков. Флаг `--models-dir PATH` принимает абсолютный путь или относительный **от текущего рабочего каталога процесса**; `--root` не меняет это правило. Ожидаемые имена: `rent.model`, `sale.model`; `evaluation.txt` для прогнозов не читается. Тип сделки внутри файла должен совпадать с именем. Изменение/удаление файлов после старта не изменяет загруженные модели: нужен отдельный перезапуск, обучение не происходит автоматически.

Если каталог не задан, сервер собран с OFF, файл отсутствует, обрезан, имеет другую версию/seed/lambda или содержит несовместимую модель, сайт продолжает работать. Причина записывается в журнал, клиенту не раскрываются внутренние пути. Отказ одной модели не выключает вторую. Проверенные модели неизменяемы и используются несколькими потоками только для чтения.

Признаки получаются из `Listing`, прочитанного SQLite: площадь, комнаты, этаж, тип, район, ремонт. В `Row.price` и `Row.propertyId` адаптер передаёт 0: они не используются `encode/predict`. Изменение цены объявления не меняет прогноз. Незнакомая категория идёт в прежний unknown-столбец; нижняя граница остаётся 1 AMD. Исключение `predict`, нечисловой результат или сумма выше `Number.MAX_SAFE_INTEGER` (9 007 199 254 740 991) дают недоступность. Последнее — ограничение безопасного представления API/UI, **не изменение модели или прежних метрик**, и не верхнее ограничение пользовательской цены. Никаких обещаний точности, рыночной справедливости или диапазона ошибки нет.

### Воспроизводимый запуск с новыми артефактами

Обычная сборка без ML остаётся возможной:


### Обновление основного сервера — отдельное действие

В этой задаче основной PID 46690 на 8080 **не перезапускался**, рабочая база не изменялась. Статика в общей папке обновлена, поэтому старый сервер без нового API показывает «недоступна». После разрешения обновления: собрать ON, подготовить модели отдельной командой (можно на отдельной демобазе), корректно остановить только основной процесс, убедиться в освобождении 8080 и запустить с прежним `--db data/apartments.sqlite3` и явным `--models-dir`. После перезапуска пользователям потребуется войти заново, так как сессии находятся в памяти. Замена моделей также требует перезапуска; файл базы или цены для этого менять не нужно.
