# Требования проекта

Учебный сайт аренды и продажи квартир и домов. Сдача репозитория на GitHub — до конца **14 сентября 2026**, защита — **16 сентября 2026**.

## Стек и принципы

- C++17, Drogon, SQLite, CMake.
- HTML, CSS, обычный JavaScript. Вся серверная бизнес-логика — на C++.
- Простая структура и понятный код для студента, изучающего C++; объяснения SQL на русском.
- Сначала обязательные требования. ML сейчас не реализуется; возможен только позже.
- DB Browser for SQLite — программа просмотра базы, а не замена библиотеки SQLite для C++.

## Полные обязательные требования

1. Около 1000 демонстрационных квартир/домов. У каждого есть адрес, район, площадь, количество комнат, этаж, цена, описание и несколько фотографий.
2. Каталог и отдельная страница каждого объявления с фотографиями и информацией о местоположении.
3. Разделение на аренду и продажу.
4. Фильтры по району, диапазону цен и комнатам; сортировка по цене или площади в обе стороны; пагинация. Выбор способа сортировки нужно обосновать.
5. Регистрация, вход и выход. Безопасное хеширование паролей готовой библиотекой и пользовательские сессии.
6. Только авторизованный пользователь может забронировать доступное объявление.
7. При одновременном бронировании двумя пользователями только один получает объект. Гарантия должна обеспечиваться базой и транзакцией, а не только интерфейсом. Нужен проверяющий это тест.
8. Личный кабинет «Мои бронирования».
9. Арендатор может освободить свой объект: то же объявление снова доступно.
10. Покупатель может выставить свой объект на продажу с новой положительной ценой: создаётся новое объявление, старое остаётся закрытым в истории. Недвижимость и объявления хранятся отдельно. Повторный запрос не должен создавать несколько доступных объявлений для одного объекта.
11. Только соответствующий пользователь может освобождать или перепродавать забронированный объект.
12. Избранное, история просмотров и простые рекомендации по районам и ценовым предпочтениям.
13. Данные сохраняются после перезапуска. Заполнение демонстрационными данными не дублирует записи и не стирает существующие данные.
14. README с точными командами установки зависимостей, сборки, подготовки базы, запуска и тестирования.

## Граница первого этапа

Проверить ОС, инструкции и зависимости; при необходимости установить зависимости через механизм разрешений. Создать собираемый проект, начальную SQL-схему, средство заполнения 12 объектами (аренда и продажа), каталог с реальными данными SQLite, `GET /api/health`, `GET /api/listings`, `.gitignore`, README и руководство по базе. Входные значения передавать параметрами SQL; внешние ключи включать для каждого соединения. Собрать, запустить, проверить каталог, сохранение данных и отсутствие дублей после повторного запуска.

Рабочую базу, сборку и секреты не включать в Git. Схему и генератор демонстрационных данных хранить в репозитории. Предусмотреть будущие бронирования, но не реализовывать регистрацию, бронирование и последующие этапы в рамках первого этапа.

## Граница третьего этапа

По отдельному заданию: регистрация, вход, выход, текущий пользователь; Argon2id, серверные сессии с HttpOnly/SameSite/Secure-настройкой, ротация и завершение сессий, CSRF и ограничение попыток входа. Миграция пользователей и истории бронирований с сохранением данных. Атомарное бронирование доступного объявления, цена на момент действия, ограничения БД, корректное ожидание конкурирующих записей. Личный кабинет показывает только свои бронирования. HTTP-гонка двух пользователей, откат при ошибке и проверки доступа обязательны; тестовые базы отдельные. Документация и локальный коммит без push. Освобождение, перепродажа, избранное, рекомендации и ML отложены.
