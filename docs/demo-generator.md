# Демонстрационный генератор, версия 2

Все коэффициенты ниже — **допущения учебного генератора**. Это не реальные предложения Еревана, не рыночная оценка и не ML. Четыре фотографии остаются повторяемыми иллюстрациями и **не отражают состояние ремонта конкретного объекта**.

## Почему прежние значения повторялись

В старом `src/seed.cpp` число комнат зависело от остатка деления на 4, добавка площади — от остатка на 13/16. Получалось небольшое число сочетаний. Цена почти напрямую следовала площади и номеру района; совпадения возникали регулярно. Старый расчёт сохранён в `legacyDemoProperty` как эталон распознавания исходных записей, а не как альтернативный режим заполнения.

## Характеристики и воспроизводимость

`demoProperty(number)` сохраняет прежние demo_key, адрес, район, тип недвижимости и тип первоначальной сделки. Для каждого номера создаётся отдельный `std::mt19937` с seed **20260913 + number**. Целые значения выбираются через остаток деления результата движка, без зависящего от реализации `uniform_*_distribution`. Это простая ограниченная псевдослучайность, не криптография. Пропуск объекта с историей не сдвигает последовательность остальных.

- Квартира: 1–5 комнат; площадь `18 × комнаты + 10 + добавка от 0 до 25 м²` с шагом 0,1 м². Этаж 1–16.
- Дом: 3–7 комнат; площадь `25 × комнаты + 30 + добавка от 0 до 60 м²` с шагом 0,1 м². `floor = 0` означает **дом целиком**, не количество этажей здания. Число этажей дома не выдумывается.
- Ремонт выбирается из четырёх состояний. Унаследованные/пользовательские объекты могут оставаться с `unspecified` («Не указано»).
- Описание строится из типа, комнат и ремонта. Для `needs_repair` прямо указана необходимость восстановительных/отделочных работ; обещаний нового ремонта нет.
- Цены и площади не обязаны быть уникальными. Время создания объявления — фактическое время первого INSERT, поэтому оно не входит в обещание воспроизводимости характеристик.

## Как рассчитывается цена

`demoPrice` считает аренду за месяц и продажу отдельно:

```text
базовая цена = площадь × ставка района × коэффициент типа × коэффициент ремонта
цена = округление(базовая цена × (1 + отклонение / 100))
```

Отклонение — целое от **−8% до +8%**. Округление до ближайших **1000 AMD** для аренды, **50 000 AMD** для продажи. Половина шага округляется вверх. Коэффициенты не зависят от пользовательской истории, а пересчёт цены никогда не меняет `price_at_booking`.

## Новая схема и безопасное обновление

`sql/006_demo_renovation.sql` добавляет два столбца `properties`:

- `renovation TEXT NOT NULL DEFAULT 'unspecified'`: CHECK разрешает только пять устойчивых значений (четыре ремонта и «Не указано»).
- `demo_revision INTEGER NOT NULL DEFAULT 0`: 0 для прежних/необработанных записей, 2 для нового генератора. Отметка 2 запрещает повторное обновление даже после последующей ручной правки.

Миграции 001–005 не изменены. Обычный `--init-db` и запуск сервера добавляют только **отсутствующие** demo_key; существующие свойства, цены и историю не обновляют. Новые демообъекты сразу получают версию 2.

Перед изменением существующей базы сделайте резервную копию **SQLite Backup API**, а не копирование работающего файла командой cp. Пример из корня проекта (уникальное имя, БД читается в режиме только чтения):

```sh
python3 - <<'PY'
from pathlib import Path
from datetime import datetime
import sqlite3
source_path = Path('data/apartments.sqlite3').resolve()
backup_path = source_path.parent / 'backups' / ('before-demo-' + datetime.now().strftime('%Y%m%d-%H%M%S-%f') + '.sqlite3')
backup_path.parent.mkdir(exist_ok=True)
with sqlite3.connect(source_path.as_uri() + '?mode=ro', uri=True) as source, sqlite3.connect(backup_path) as backup:
    source.backup(backup)
    assert backup.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
    assert not backup.execute('PRAGMA foreign_key_check').fetchall()
print(backup_path)
PY
./build/apartment_server --preview-demo-update
./build/apartment_server --update-demo-data
```

Можно добавить `--db /путь/к/копии.sqlite3`. Обе команды завершаются без запуска HTTP-сервера; отсутствующий файл базы не создают. Предварительный просмотр может применить **только ещё не применённую миграцию**, добавив столбцы со значениями по умолчанию; характеристики и цены он не меняет. Обе команды не заполняют недостающие demo_key. Для новых баз служит обычный `--init-db`.

Каждый из 1000 исходных ключей проверяется в `src/demo_refresh.cpp`:

1. При любом бронировании объекта/его объявления, избранном, просмотре, происхождении от перепродажи или количестве объявлений, отличном от одного, объект пропускается целиком. Учитываются **все состояния** бронирования, а не только active.
2. Версия 2 пропускается как уже обработанная.
3. Все прежние характеристики, координаты, адрес, описание, тип/цена/status/demo_key объявления и все подписи/URL/порядок фотографий должны **точно совпасть** с прежним эталоном. Любое отличие означает спорную запись и пропуск. Один demo_key не считается достаточным доказательством.
4. Только area, rooms, floor, description, renovation, demo_revision объекта и price исходного объявления обновляются. Идентификаторы, даты создания, адреса, типы сделок, пользователи и фотографии остаются прежними. Пользовательские объявления вне этих ключей вообще не рассматриваются.

Проверка и весь пакет UPDATE выполняются внутри **одной BEGIN IMMEDIATE / COMMIT**. Другой писатель не может вклиниться между проверкой истории и изменением. При ошибке весь пакет откатывается. Ожидание SQLite ограничено 5 секундами; при превышении команда завершается ошибкой, её можно повторить позже. Повторная команда заново проверяет текущие связи, а не доверяет устаревшему предварительному числу. Сессии при выполнении команды не затрагиваются.

Проверка опирается на сохранённые строки SQLite. Удалённые вручную следы действий или ручную правку, полностью возвращённую к исходным значениям, восстановить невозможно; полного журнала всех ручных правок прежняя схема не имела. При обнаруживаемом сомнении запись не перезаписывается.

## Запросы только для чтения в DB Browser

```sql
SELECT l.deal_type, COUNT(*) AS listings,
       COUNT(DISTINCT p.area) AS distinct_areas,
       COUNT(DISTINCT l.price) AS distinct_prices
FROM listings AS l JOIN properties AS p ON p.id = l.property_id
GROUP BY l.deal_type;

SELECT renovation, COUNT(*) AS properties
FROM properties GROUP BY renovation ORDER BY renovation;

SELECT p.id, p.address, p.kind, p.area, p.rooms, p.floor,
       p.renovation, l.deal_type, l.price, l.status
FROM properties AS p JOIN listings AS l ON l.property_id = p.id
WHERE p.address LIKE 'Ереван, ул. Сарьяна,%'
ORDER BY p.id, l.id;
```

`COUNT(DISTINCT ...)` считает количество разных значений, а не число объектов. Первый запрос разделяет аренду и продажу, поэтому месячные цены не смешиваются с полной стоимостью.
