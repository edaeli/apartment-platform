### Гонка и транзакция — выполнено через HTTP

`tests/auth_http.py` запускает настоящий сервер с **двумя рабочими потоками Drogon**. Обработчик каждой операции открывает собственное соединение SQLite. Два разных зарегистрированных пользователя имеют отдельные cookie и CSRF-токены. `threading.Barrier` синхронизирует начало их HTTP-запросов.

Сценарий повторён на пяти свободных объявлениях (21–25). В каждом случае проверено:

- ровно один ответ **201** и один **409**;
- сообщение проигравшему: **«Это жильё уже забронировали»**;
- в SQLite ровно одна запись бронирования, она активна;
- `user_id` записи совпадает с пользователем, получившим 201;
- объявление имеет состояние `reserved`.

Отдельно выполнены успешный и повторный запрос, 404 неизвестного объявления, проверка зафиксированной цены после изменения цены объявления в тестовой базе.

Для проверки отката создан временный `BEFORE INSERT ON bookings` триггер, который выдаёт ошибку **после UPDATE статуса**. Получен 500; объявление осталось `available`, бронирований не появилось. После удаления тестового триггера новое действие прошло.

Для проверки занятости независимое соединение держало `BEGIN IMMEDIATE`: HTTP получил **503** после ограниченного ожидания, статус и записи не изменились. После освобождения блокировки повтор прошёл. Краткая блокировка 350 мс также проверена: запрос смог завершиться после её снятия.

Перезапуск HTTP-сервера и отдельный повторный `--init-db` сохранили **все строки пяти таблиц**. Старые сессии после перезапуска недействительны; после нового входа прежние бронирования снова видны. `integrity_check = ok`, `foreign_key_check` пуст.
