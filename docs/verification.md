### Конкурентные действия и полный откат — выполнено через HTTP

Реальный Drogon-сервер работает с **двумя потоками**, каждая операция открывает отдельное соединение SQLite. В `lifecycle_http` две независимые авторизованные сессии одного владельца стартуют через `threading.Barrier`; именно владелец может выполнять оба действия.

- **5 пар освобождений:** в каждой ровно один 200 и один 409. Объявление available; после бронирования другим пользователем запоздалый POST прежнего арендатора получает 409. Снимки **всех пяти таблиц** до/после такого повтора совпадают, включая дату завершения и новое бронирование.
- **5 пар перепродаж с разными ценами:** в каждой один 201 и один 409, в SQLite ровно одно новое объявление для исходного бронирования. Цена совпадает с запросом победителя, продавец правильный, незакрытое объявление объекта ровно одно.
- Искусственный триггер отклоняет UPDATE объявления **после** изменения бронирования: и для освобождения, и для перепродажи получен 500, все таблицы совпадают с состоянием до запроса.
- Отдельно смоделировано несоответствие прежнего статуса объявления: UPDATE меняет ноль строк, ответ 409, завершение бронирования также откатывается.
- Для перепродажи второй триггер отклоняет последний INSERT **после** завершения бронирования и закрытия старого объявления. Ответ 500; прежняя запись снова active без ended_at, прежнее объявление reserved, нового нет. Полные снимки таблиц совпадают. После удаления тестового триггера действие успешно.
- Другое соединение удерживает BEGIN IMMEDIATE: освобождение/перепродажа возвращают **503** за ограниченное время (проверено больше 0,5 и меньше 4 с), без изменений. После снятия блокировки повтор проходит. Это отдельно от гонок 200/201+409; занятость базы не выдается за уже выполненную операцию.

### Гонка и транзакция — выполнено через HTTP

`tests/auth_http.py` запускает настоящий сервер с **двумя рабочими потоками Drogon**. Обработчик каждой операции открывает собственное соединение SQLite. Два разных зарегистрированных пользователя имеют отдельные cookie и CSRF-токены. `threading.Barrier` синхронизирует начало их HTTP-запросов.

Сценарий повторён на пяти свободных объявлениях (21–25). В каждом случае проверено:

- ровно один ответ **201** и один **409**;
- сообщение проигравшему: **«Это жильё уже забронировали»**;
- в SQLite ровно одна запись бронирования, она активна;
- `user_id` записи совпадает с пользователем, получившим 201;
- объявление имеет состояние `reserved`.

Отдельно выполнены успешный и повторный запрос, 404 неизвестного объявления, проверка зафиксированной цены после изменения цены объявления в тестовой базе.
