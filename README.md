# Свой адрес — учебный каталог недвижимости

Работающая основа сайта аренды и продажи квартир и домов: **C++17 + Drogon + SQLite + CMake**, интерфейс на HTML/CSS/обычном JavaScript. Все обращения к базе и серверная логика находятся в C++.

Завершены этапы 1–5: **1000 демонстрационных объектов в Ереване**, 500 первоначальных объявлений аренды и 500 продажи, квартиры и дома в 9 районах. Каталог поддерживает совместные фильтры, четыре сортировки, пагинацию и отдельные страницы объявлений с фотографиями. Цены в AMD; аренда — **в месяц**.

Четыре локальных JPEG из Unsplash повторяются в объявлениях: гостиная или внешний вид дома, кухня и спальня. У каждого демообъекта три записи фотографий, всего 3000. Это иллюстрации, **не реальные фотографии указанных адресов**. Источники и лицензия: [public/images/README.md](public/images/README.md). Адреса, характеристики и цены учебные; точная карта не показывается. Для работы после установки зависимостей интернет не нужен.

Работают регистрация, вход, выход, серверные сессии, бронирование, освобождение аренды и перепродажа покупки с сохранением истории. В «Моих бронированиях» разделены активные записи и история. Добавлены избранное, история просмотров и рекомендации по простым правилам. Рекомендации работают без ML; необязательная оценка цены включается отдельно. Полные требования: [docs/requirements.md](docs/requirements.md), последовательность работы: [docs/plan.md](docs/plan.md).

## Запуск на Ubuntu 24.04 LTS

Полная инструкция для преподавателя: [docs/ubuntu.md](docs/ubuntu.md). Она включает зависимости, Drogon 1.9.13, получение ветки с ML, обе сборки, новую демобазу, обучение, HTTP и тесты. **Ubuntu пока не проверена фактически**; macOS-проверки не заменяют Linux. Текущая ML-ветка ещё не опубликована: в инструкции есть вариант передачи через Git bundle без push.

## Установка зависимостей на этом Mac

Проверенная среда: macOS 15.0, Apple Silicon (arm64), Apple Clang 15.0.0, CMake 4.3.4, Git 2.39.3, Drogon 1.9.13, SQLite 3.53.4 и libsodium 1.0.22 из Homebrew. Python 3 (минимум 3.8) используется только в интеграционных тестах; сервер его не вызывает. CMake выводит выбранный интерпретатор: в проверке чистой копии это установленный Python 3.11.5 из Anaconda, тогда как `python3` в терминале — 3.11.2. Путь к Anaconda в проекте не задан; Homebrew Python также можно выбрать через `-DPython3_EXECUTABLE="$(command -v python3)"`.

Проверить инструменты:

```sh
sw_vers
uname -m
c++ --version
cmake --version
git --version
brew --version
drogon_ctl version
python3 --version
```

Apple Command Line Tools уже установлены. Если `c++` или `git` отсутствует на другом Mac, запустите установку и дождитесь её завершения:

```sh
xcode-select --install
```

Homebrew на текущем Mac находится в `/opt/homebrew`. При его отсутствии используйте официальный установщик на [brew.sh](https://brew.sh/). Установка зависимостей проекта:

```sh
brew install cmake drogon sqlite libsodium
```

`drogon` устанавливает веб-фреймворк и необходимые ему библиотеки; `sqlite` — библиотеку, заголовки для C++ и консольную утилиту. `libsodium` — проверенная библиотека Argon2id и криптографических случайных чисел. **DB Browser for SQLite этого не заменяет.** Если Python 3 отсутствует и нужны тесты:

```sh
brew install python
```

Homebrew SQLite не подменяет системный `/usr/bin/sqlite3`. Проект выбирает Homebrew-библиотеку через `CMAKE_PREFIX_PATH`; менять глобальный `PATH` не требуется. Версию можно посмотреть так:

```sh
"$(brew --prefix sqlite)/bin/sqlite3" --version
```

## Сборка на macOS

Откройте терминал в корне полученной копии (в этой папке должен быть `CMakeLists.txt`). Все дальнейшие команды выполняются оттуда; путь к домашней папке автора не нужен:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DCMAKE_PREFIX_PATH="$(brew --prefix);$(brew --prefix sqlite)" -DBUILD_TESTING=ON
cmake --build build -j 4
```

Для сборки только сервера без Python: при конфигурации укажите `-DBUILD_TESTING=OFF`. Сборка проекта использует `-std=c++17`, даже если установленная готовая библиотека Drogon была собрана другой версией стандарта.

## Подготовка базы и запуск

```sh
./build/apartment_server --init-db
./build/apartment_server
```

Откройте **http://127.0.0.1:8080/**. Пример прямой страницы: **http://127.0.0.1:8080/listings/1**. Обновление этой страницы работает. Сервер остаётся работать в терминале; остановка — **Ctrl+C**.

Перед запуском проверьте, свободен ли порт:

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

Если наш сервер уже работает, откройте его адрес. После пересборки остановите старый процесс через Ctrl+C в его терминале и только затем запускайте новый. Если порт занят другим приложением, выберите `--port 8081`.

`--init-db` создаёт схему, добавляет отсутствующие демообъекты и завершает программу. Обычный запуск делает ту же подготовку автоматически, затем запускает сайт. Обе команды можно повторять: существующие записи, цены, состояния и фотографии сохраняются. Схемы 1–5 автоматически обновляются до версии 6 последовательными миграциями. `sql/002_catalog_indexes.sql` добавляет индексы, `sql/003_users_bookings.sql` — пользователей, бронирования и ограничения, `sql/004_resale_origin.sql` — продавца и связь нового объявления с исходным бронированием, `sql/005_personalization.sql` — избранное и просмотры. `sql/006_demo_renovation.sql` добавляет состояние ремонта и отметку версии демогенератора, не меняя прежние характеристики и цены. Старые таблицы не пересоздаются. Уже применённые миграции повторно не выполняются; пользователи, бронирования, избранное и история просмотров не затрагиваются генератором.

Генератор версии 2 добавляет отсутствующие ключи до `demo-1000`. Фиксированный seed, согласованные комнаты/площади/этажи и ремонт дают воспроизводимые характеристики. Цены рассчитываются отдельно для аренды и продажи по учебным коэффициентам площади, района, типа и ремонта с отклонением ±8%; округление до 1000/50000 AMD. Это не рыночная оценка. Существующие объекты при обычном запуске пропускаются целиком, число объявлений не ограничивается 1000. `created_at` отражает время первого создания.

Для обновления прежних **неизменённых** демоданных после резервной копии предусмотрены отдельные команды:

```sh
./build/apartment_server --preview-demo-update
./build/apartment_server --update-demo-data
```

Объект с любыми сохранёнными бронированиями, перепродажами, избранным или просмотрами пропускается целиком; спорные и вручную изменённые строки также пропускаются. Повторное обновление ничего не меняет. Подробная процедура резервного копирования, критерии безопасности, коэффициенты и статистика до/после: [docs/demo-generator.md](docs/demo-generator.md).

Ремонт показывается на подробной странице и карточке: «Требует ремонта», «Косметический», «Хороший», «Дизайнерский»; у защищённых старых объектов — «Не указано». Фотографии не отражают ремонт конкретного объекта. Команда обновления не завершает сессии работающего процесса. Однако для нового поля API нужна новая версия сервера: обычный перезапуск завершает входы, поскольку сессии хранятся в памяти.

Файл базы по умолчанию — `data/apartments.sqlite3` внутри запущенной копии проекта. Абсолютный путь для DB Browser можно получить из корня копии:

```sh
python3 -c 'from pathlib import Path; print(Path("data/apartments.sqlite3").resolve())'
```

Другой порт (например, если 8080 занят):

```sh
./build/apartment_server --port 8081
```

Явные пути позволяют запускать из любой папки. Сначала сохраните путь, находясь в корне нужной копии:

```sh
project_root="$PWD"
"$project_root/build/apartment_server" --root "$project_root" --db "$project_root/data/apartments.sqlite3" --port 8080
```

`--root` указывает папку с `sql/` и `public/`; `--db` — файл SQLite (относительный путь считается от текущей папки терминала). По умолчанию база находится в `ROOT/data/apartments.sqlite3`. Сервер слушает только `127.0.0.1`. Статические файлы отдаются только из `public/`, база находится вне этой папки. Локальные рабочие каталоги Drogon также размещаются рядом с базой.

## API

```sh
curl --fail http://127.0.0.1:8080/api/health
curl --fail 'http://127.0.0.1:8080/api/listings?type=rent&min_price=200000&max_price=500000&rooms=2&sort=price_asc&page=1&page_size=24'
curl --fail --get http://127.0.0.1:8080/api/listings --data-urlencode 'district=Кентрон' --data-urlencode 'type=rent' --data-urlencode 'sort=area_desc'
curl --fail http://127.0.0.1:8080/api/listings/1
```

`GET /api/health` читает базу и возвращает состояние, версию SQLite/схемы, внешние ключи и количество объектов/объявлений. При недоступной базе — 503.

`GET /api/listings` принимает необязательные параметры; отсутствующий фильтр не ограничивает выборку:

| Параметр | Допустимые значения / по умолчанию |
| --- | --- |
| `type` | `rent` или `sale`; по умолчанию обе сделки |
| `district` | Точное название района, до 100 байт UTF-8, без управляющих символов; неизвестный район даёт пустую выдачу |
| `min_price`, `max_price` | Целые от 0 до 1 000 000 000 000 драмов включительно; минимум не больше максимума |
| `rooms` | Целое от 1 до 100, точное количество комнат |
| `sort` | `price_asc` (по умолчанию), `price_desc`, `area_asc`, `area_desc` |
| `page` | Целое от 1 до 1 000 000; по умолчанию 1 |
| `page_size` | Целое от 1 до 100; по умолчанию 24 |

Пример метаданных ответа без фильтров (поле `items` здесь не показано):

```json
{
  "count": 24,
  "total": 1000,
  "page": 1,
  "page_size": 24,
  "total_pages": 42,
  "has_previous": false,
  "has_next": true,
  "districts": ["Аван", "Аджапняк", "Арабкир", "Канакер-Зейтун", "Кентрон", "Малатия-Себастия", "Нор Норк", "Шенгавит", "Эребуни"]
}
```

`items` в настоящем ответе содержит 24 записи; `count` — их число на текущей странице, `total` — число подходящих объявлений **до** пагинации. `districts` — полный список районов из базы для формы, независимо от выбранных фильтров. При отсутствии результатов: `items: []`, `count: 0`, `total: 0`, `total_pages: 0`. Слишком далёкая допустимая страница даёт пустой `items`, сохраняя реальный `total`.

Все фильтры соединяются через `AND`. Выборка, сортировка и пагинация выполняются в SQLite. При равном значении цена/площадь используется `l.id ASC`. `COUNT` и выборка страницы читают один снимок базы в транзакции. Фотографии присоединяются **после** ограничения страницы, поэтому 3 фото не превращают одно объявление в 3 места выдачи.

Ошибочные, пустые, повторяющиеся или неизвестные параметры, неверные числа и сортировки дают **400** с JSON `{"error":"понятное объяснение"}`. Значения передаются через `sqlite3_bind_*`; фрагменты `ORDER BY` выбираются из четырёх фиксированных вариантов. Ошибки чтения базы — 500.

`GET /api/listings/{id}` возвращает одно объявление со всеми фотографиями, адресом, характеристиками, ценой, описанием и состоянием. Забронированное или закрытое объявление доступно по прямому адресу, но отсутствует в каталоге. Несуществующий положительный `id` — **404**, нечисловой/неположительный/переполненный — **400**. `GET /listings/{id}` отдаёт HTML-страницу, которая получает эти данные из API; для отсутствующего объявления HTML тоже имеет статус 404 и показывает понятное сообщение.

Обоснование сортировки, индексов, `LIMIT/OFFSET` и полные SQL-примеры: [database-guide.md](docs/database-guide.md), [catalog-queries.sql](docs/catalog-queries.sql). Фактические планы: [query-plans.md](docs/query-plans.md). Универсально самого быстрого плана не предполагается.

## Использование каталога

Выберите сделку, район, цены и комнаты, затем нажмите **«Показать»**. Переключение сделки и сортировки применяется сразу. Применение изменённых условий возвращает страницу 1. **«Сбросить»** очищает условия и восстанавливает стандартную выдачу. Номер страницы меняется ссылками под карточками.

Параметры сохраняются в URL: адрес можно скопировать, обновить или открыть заново; кнопки браузера «Назад/Вперёд» восстанавливают выборку. Нажатие на фотографию или заголовок открывает объявление. **«Вернуться в каталог»** сохраняет условия и страницу, если объявление открыто из каталога. Миниатюры переключают большое фото.

Есть загрузка, сообщение об ошибке с повтором, пустой результат, 404 и заглушка для отсутствующего/недоступного фото. Текст из базы вставляется через `textContent`. На доступной странице объявления вошедшему пользователю показана кнопка «Арендовать» или «Купить». Гость получает ссылку на вход. После входа нужно нажать кнопку самостоятельно; реальной оплаты нет.

## Вход и бронирование

1. Откройте объявление и нажмите «Войти для бронирования»; при необходимости перейдите к регистрации. Имя — 2–80 символов, обычный email латиницей, пароль — 8–128 байт UTF-8. Пробелы по краям email убираются, латинские буквы приводятся к нижнему регистру. Для пароля пробелы не удаляются. Подтверждения email и восстановления пароля пока нет.
2. После регистрации/входа сайт возвращает на исходную страницу. Бронирование само не создаётся.
3. Нажмите «Арендовать» или «Купить». Это **бронирование внутри учебного сайта, без оплаты и без реальной сделки**. Пока запрос выполняется, кнопка отключена. После успеха состояние меняется на «Забронировано» и появляется ссылка в личный кабинет.
4. В «Мои бронирования» видны только ваши записи: объект и фото, тип сделки, цена при бронировании, дата и состояние. Даже если позднее цена объявления изменится, зафиксированная цена останется прежней.
5. Если другой пользователь успел первым, сайт сообщает «Это жильё уже забронировали» и обновляет объявление. У занятого/закрытого объявления кнопки действия нет. После выхода личный кабинет требует входа заново.

## Освобождение и перепродажа

В `/my-bookings` активные записи и история показаны отдельно. Действия доступны только владельцу **активного** бронирования нужного типа:

- **Аренда → «Освободить» → «Да, освободить»**: запись переходит в историю с состоянием «Освобождено» и датой завершения. То же объявление снова доступно; другой пользователь может арендовать его. «Отмена» закрывает подтверждение без изменений.
- **Покупка → «Выставить на продажу»**: введите новую цену и нажмите «Опубликовать объявление». Появится ссылка на новое доступное объявление. Старое останется закрытым по прежнему адресу; исходная цена бронирования и дата завершения видны в истории. Адрес, характеристики и фотографии принадлежат прежнему объекту, их копии не создаются.

Цена — от **1 до 1 000 000 000 000 драмов включительно**, только целое число. Например, `55000000`. Пробелы, знак, дробь и экспоненциальная запись не принимаются. Во время запроса кнопки и поля отключены. Продавец видит пояснение вместо кнопки покупки своего нового объявления; другой пользователь может его забронировать. Перепродажа — учебная операция без платежей и оформления реального права собственности.

Старая запись в истории не даёт права действовать снова: запоздалое освобождение не затронет нового арендатора, повторная перепродажа не создаст ещё одно объявление. При конфликте кабинет загружает актуальное состояние. Каталог продолжает показывать только доступные объявления с прежними фильтрами, сортировкой и пагинацией.

Для демонстрации без изменения рабочей базы можно запустить отдельную тестовую базу:

```sh
./build/apartment_server --db /tmp/apartment-manual-stage4.sqlite3 --port 8082
```

Сначала убедитесь, что порт 8082 свободен. При повторном использовании этого пути данные тестовой базы также сохраняются. Для совершенно нового демонабора выберите другое имя файла. Cookie привязаны к хосту, а не порту: не входите попеременно в два независимых сервера на `127.0.0.1` в одном профиле браузера. Для проверки двух пользователей используйте обычное и приватное окно **одного адреса**.

## API авторизации и бронирования

| Метод и адрес | Назначение / результат |
| --- | --- |
| `GET /api/auth/me` | Профиль `{id,name,email,created_at}` или `user: null`, а также `csrf_token`; создаёт гостевую сессию, если её ещё нет |
| `POST /api/auth/register` | JSON `{name,email,password}`, создаёт пользователя и выполняет вход; 201; повтор email — 409 |
| `POST /api/auth/login` | JSON `{email,password}`, меняет идентификатор сессии; 200; неверные данные — 401 |
| `POST /api/auth/logout` | JSON `{}`, удаляет сессию на сервере и cookie; 200 |
| `POST /api/listings/{id}/book` | JSON `{}`, идентификатор пользователя берётся только из сессии; 201 с id бронирования |
| `GET /api/bookings` | `{items:[...]}`, только собственные активные и завершённые бронирования; `ended_at`, исходная цена и `resale_listing_id` (id нового объявления или null); гостю 401 |
| `POST /api/bookings/{id}/release` | JSON `{}`; 200, завершает конкретное бронирование аренды и освобождает прежнее объявление |
| `POST /api/bookings/{id}/resell` | JSON `{"price":"55000000"}`; 201 с `listing_id` нового объявления и `booking_id` завершённого бронирования |

Каждый изменяющий запрос (POST, PUT, DELETE) требует cookie сессии, `Content-Type: application/json` и заголовок `X-CSRF-Token` из последнего `/api/auth/me` или успешного ответа входа/регистрации. Токен меняется вместе с сессией. Без него — 403, в том числе на формах регистрации/входа/выхода. Если `Origin` передан, он должен совпасть с настроенным адресом; `Sec-Fetch-Site: cross-site` отклоняется. Запросы обычного HTTP-клиента без `Origin` допустимы с правильным CSRF-токеном. CORS-доступ чужим сайтам не разрешён.

API не принимает `user_id` и неизвестные поля; цену принимает только `/resell`. Первоначальное бронирование берёт цену из SQLite. API авторизации и действий с бронированиями не принимают query-параметры. У личных списков и рекомендаций есть только параметры, перечисленные ниже. Некорректный JSON, поля, email, пароль или id — 400. Для бронирования: гостю 401, отсутствующему объявлению 404, занятому/закрытому — 409, продавцу собственного объявления — 403. Длительная блокировка БД — 503 с просьбой повторить позже; ошибка вставки — 500 с откатом изменения статуса. UI никогда не повторяет POST автоматически.

`/resell` принимает цену как строку из цифр либо JSON-число в целой записи. Сервер проверяет тип, формат, диапазон 1–1 000 000 000 000 и переполнение `int64_t`. Записи `1.0`, `1e3`, отрицательные, нулевые, слишком большие значения и нечисловые типы дают 400 без изменений. UI передаёт исходную строку.

У освобождения/перепродажи: гость — 401; чужое бронирование — 403; отсутствие CSRF — 403; неизвестное бронирование — 404; неверный тип сделки, уже завершённая запись или несоответствие статуса объявления — 409. GET по адресам действий ничего не меняет (в проверенном Drogon — 404). Ошибки внутри транзакции откатывают все шаги, длительная блокировка даёт 503, а не ложный успех. В ответах объявлений также есть `created_at`, `seller_user_id` и `source_booking_id`; у первоначальных объявлений две последние связи равны null. Чужие личные данные и записи бронирований через эти id не выдаются.

## Избранное, история и рекомендации

На карточке и подробной странице есть **«♡ В избранное»** и **«♥ Убрать из избранного»**. Гостю предлагается войти; после входа нужно нажать самостоятельно. На сервер отправляются отдельные PUT/DELETE: повторное добавление не создаёт дубль и не меняет дату, повторное удаление допустимо. Пока запрос выполняется, повторное нажатие отключено.

Страница **http://127.0.0.1:8080/favorites** показывает ваши сохранённые объявления, по 24 на страницу (максимум API — 100). Страница записывается в URL. Занятые и закрытые объявления сохраняются с правильными состояниями и прежними ссылками: перепродажа не переносит избранное на новое объявление.

**http://127.0.0.1:8080/view-history** — личная история с пагинацией, временем последнего учтённого открытия и счётчиком. Только открытие подробной страницы вошедшим пользователем отправляет защищённый POST просмотра. Каталог, карточки, GET API и подборка не записывают просмотры. Повтор одного объявления одним пользователем в течение **30 минут** не меняет ни счётчик, ни время. Время задаёт сервер; при обновлении страницы после 30 минут просмотр учитывается снова. История сохраняется в SQLite, без IP или отпечатка браузера. Редактирования истории через API нет.

На главной блок **«Вам может понравиться»** показывает до 6 объявлений. Используются последние 100 избранных (вес **3**) и 100 просмотренных, отсутствующих в избранном (вес **1**). Счётчик повторных просмотров не увеличивает вес. Для каждого типа сделки отдельно оцениваются совпадение района и близость цены: месячная аренда никогда не сравнивается с полной ценой продажи. Оценки детерминированы, равенство разрешается по id. В подборку входят только available, исключены собственные и все избранные объявления. Просмотренные варианты могут встречаться снова.

У гостя или без подходящих предпочтений показывается **обычная подборка доступного жилья**, с явной подписью. Недостаток совпадений дополняется доступными вариантами без дублей; в их пояснении нет утверждения о персонализации. Рекомендации обновляются после изменения избранного на главной; после просмотра другого объявления вернитесь на главную или обновите её.

Точные веса, границы цены, формула и пример с расчётом — в разделе «Рекомендации без ML» [руководства по базе](docs/database-guide.md). Это учебные правила, а не прогноз цен или оценка качества жилья. Изменения предпочтений не сбрасывают фильтры каталога.

| Метод и адрес | Назначение |
| --- | --- |
| `PUT /api/favorites/{id}` | JSON `{}`, добавить конкретное объявление; 200 и `is_favorite: true`, в том числе при повторе |
| `DELETE /api/favorites/{id}` | JSON `{}`, удалить свою пару; 200 и `is_favorite: false`, в том числе при повторе |
| `GET /api/favorites?page=1&page_size=24` | Только свой список: `items`, `total`, `count`, `page`, `page_size`, `total_pages`; у карточки `saved_at` |
| `POST /api/listings/{id}/view` | JSON `{}`, записать просмотр; 200, `counted: true/false` в зависимости от окна 30 минут |
| `GET /api/views?page=1&page_size=24` | Только своя история; те же метаданные, `last_viewed_at` (Unix-секунды UTC) и `view_count` |
| `GET /api/recommendations?limit=6` | Для текущей сессии или гостя; `items`, `count`, `personalized`; у карточек целый `score` 0–800 и подтверждаемое им `reason` |

Страницы личных списков требуют входа, API гостю даёт 401. Все изменяющие запросы требуют прежних cookie/CSRF/Origin-проверок; без CSRF — 403. Не принимаются user_id, собственное время, счётчик и неизвестные поля. Неизвестное объявление в действии — 404; неверные параметры — 400; длительная блокировка SQLite — 503 с полным откатом и ограниченным ожиданием. PUT/DELETE не меняют списки других пользователей.

У списков `page` 1–1 000 000, `page_size` 1–100, по умолчанию 1/24. У рекомендаций `limit` 1–24, по умолчанию 6. Эти параметры записываются цифрами ASCII без знака/дроби/кодирования; повторные и посторонние параметры отклоняются. API каталога и объявления теперь возвращает `is_favorite` **для текущей сессии**; ответы не кэшируются. Новые личные таблицы сохраняются после перезапуска, повторный вход восстанавливает доступ к ним.

## Пароли, сессии и границы локальной версии

Пароль обрабатывается `crypto_pwhash_str_alg` из libsodium с **Argon2id**, настройками `INTERACTIVE` (в установленной версии 64 MiB памяти, 2 прохода). Случайная соль создаётся библиотекой. В SQLite сохраняется только строка с алгоритмом, параметрами, солью и хешем. Проверка выполняется `crypto_pwhash_str_verify`; для неизвестного email также выполняется проверка фиктивного хеша. Хеши не входят в JSON, пароли и токены не записываются в журнал. [Документация libsodium](https://doc.libsodium.org/password_hashing/default_phf).

Сессии хранятся **в памяти одного процесса C++**, срок — **12 часов с момента создания**, без продления при чтении. Вход и регистрация создают новые независимые случайные идентификаторы сессии и CSRF (по 32 случайных байта). Старая сессия текущего браузера удаляется; вход в другом браузере не завершает уже существующий вход. Выход завершает текущую сессию. Уже начатый до выхода запрос может завершиться. После перезапуска сервера все должны войти снова; пользователи и бронирования остаются в SQLite. Просроченные записи удаляются при обращении/создании; ограничение — 4096 сессий.

Cookie `apartment_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`, `Max-Age=43200`. JavaScript видит CSRF-токен, но не секретную cookie. CSRF-токен хранится в памяти страницы, не в URL и не в localStorage. `SameSite` дополняет проверку токена. [Рекомендации OWASP по CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Для локального **HTTP** `Secure` выключен, иначе браузер может не отправлять cookie. Для **HTTPS за настроенным reverse proxy** нужны оба параметра:

```sh
./build/apartment_server --secure-cookies --origin https://housing.example
```

Это пример параметров, а не готовое развёртывание: сертификат и reverse proxy в проект не включены. Сам C++ сервер продолжает слушать HTTP только на `127.0.0.1`. Не используйте обычный локальный HTTP как публичный сервис. По умолчанию разрешён Origin `http://127.0.0.1:8080` или `http://localhost:8080` (порт берётся из `--port`); пользовательский `--origin` заменяет этот список.

Лимит входа: до 5 попыток на нормализованный email и до 30 на IP за окно 5 минут; учитываются успешные и неудачные попытки. Регистрация — до 10 на IP за 5 минут. Превышение даёт 429 и `Retry-After: 300`. Окно начинается с первой попытки; записи лимитов тоже живут в памяти, максимум 10000 ключей. После перезапуска лимиты сбрасываются. Это ограничение учебной версии с одним процессом, не распределённая защита от DDoS. IP берётся из соединения, `X-Forwarded-For` не принимается на веру; за прокси все клиенты разделяли бы его IP-лимит до отдельной настройки доверенного прокси.

SQLite допускает одного пишущего участника одновременно. Бронирование, освобождение и перепродажа используют 4 попытки **всей** транзакции `BEGIN IMMEDIATE`, ожидание SQLite до 250 мс за попытку и паузы 25/50/75 мс. Исчерпание ожидания означает временную занятость БД, а не занятое жильё. Время не является жёстким SLA: планирование потоков и дисковый ввод-вывод добавляют задержку. Сервер работает с 2 потоками и отдельным соединением БД на операцию. Хеширование/SQL синхронные; для большой нагрузки понадобятся отдельные исполнители, общий сервис сессий и более подходящая архитектура. «Мои бронирования» пока без пагинации.

- `personalization_http` (Python): переход 4 → 5 с сохранением перепродажи; PUT/DELETE, по пять гонок добавления/удаления, уникальность пары, приватность/CSRF/ошибки; пагинация закрытых/занятых избранных, отдельная запись просмотра/30 минут/гонка, отсутствие записи через GET; рекомендации, существующие освобождение/перепродажа, блокировки и сохранение **всех семи таблиц** после перезапуска/генератора.

HTTP-тесту в песочнице помощника требуется разрешение на локальный порт. В обычном терминале специальный флаг не нужен. Подробности реально выполненных проверок и ограничения браузерной проверки — [verification.md](docs/verification.md).


Короткие синхронные операции SQLite выполняются непосредственно в C++ обработчиках Drogon; соединения не разделяются между потоками. Для небольшого учебного каталога это понятная отправная точка. Перед ростом нагрузки можно добавить отдельные потоки работы с БД без изменения предметной модели.

`.gitignore` исключает базы и журналы, сборки, `.env`, ключи и локальные настройки IDE. SQL, генератор, тесты и фотографии входят в исходники. Перед будущей публикацией проверьте `git status --short`; база не должна попасть в отслеживаемые файлы. Публикация на GitHub в текущем этапе не выполняется.

## Воспроизводимость и границы проверки

Чистая копия из Git проверяется без рабочей базы, сборки, `.env` и локальных настроек: CMake → сборка → `--init-db` → CTest → сервер. Команда `--init-db` одновременно создаёт/обновляет схему и добавляет отсутствующие демонстрационные данные; отдельного скрытого скрипта заполнения нет. Если основной сайт работает на 8080, проверьте свободный порт (`lsof -nP -iTCP:8082 -sTCP:LISTEN`) и запускайте копию командой `./build/apartment_server --port 8082` из её корня. Её база будет собственной, в `data/` этой копии. Повторный `--init-db` не сбрасывает изменения.

Проверка на этом Mac использует **уже установленные зависимости** и не доказывает установку на чистой ОС. Ubuntu 24.04 LTS и Windows фактически не проверены. Для Ubuntu подготовлена отдельная [инструкция](docs/ubuntu.md); команды Homebrew выше относятся только к macOS. Версии зависимостей не закреплены lock-файлом: будущие обновления Homebrew потребуют повторной сборки и тестов. Node.js CLI в текущем окружении отсутствует; дополнительный JS-тест выполнялся доступным Node REPL.

Статус требований: [acceptance-checklist.md](docs/acceptance-checklist.md). Фактические команды и результаты: [verification.md](docs/verification.md). Браузерная проверка последнего интерфейса остаётся невыполненной. Сессии локального сервера хранятся в памяти 12 часов и завершаются при перезапуске; пользователи и предметные данные сохраняются в SQLite. Email не подтверждается, восстановления пароля нет. Реальные платежи не реализованы. Необязательная ML-оценка описана ниже.

## Необязательный учебный ML-эксперимент

Опция `BUILD_PRICE_ML=ON` (по умолчанию OFF) собирает C++ CLI обучения и поддержку сохранённых моделей в сервере. Обучение выполняется только отдельной командой; сервер загружает `rent.model` и `sale.model` один раз из `--models-dir`. Оценка показывается только в подробностях объявления и не меняет цену или рекомендации. Без моделей либо в сборке OFF сайт работает, оценка недоступна. Данные синтетические; прогноз не является рыночной оценкой.

Пример с новой отдельной демобазой, из корня проекта после установки зависимостей:

```sh
cmake -S . -B build -DBUILD_PRICE_ML=ON
cmake --build build -j 4
./build/apartment_server --db build/ml-demo.sqlite3 --init-db
./build/price_ml --db build/ml-demo.sqlite3 --out build/ml-demo-models
lsof -nP -iTCP:8082 -sTCP:LISTEN
# Запускать только если 8082 свободен:
./build/apartment_server --root . --db build/ml-demo.sqlite3 --port 8082 --models-dir build/ml-demo-models
```

Каталог `--out` должен быть новым; при повторе используйте готовые модели или другое имя. Относительный `--models-dir` считается от текущей папки терминала, не от `--root`; путь с пробелами заключайте в кавычки. Без флага поиск моделей не выполняется. Ошибки файлов журналируются отдельно для каждой сделки. После замены файлов нужен перезапуск сервера; сессии при этом завершаются, данные SQLite сохраняются. Не перезапускайте основной сервер ради тестового примера. Полные команды чистой сборки, тестов, метрики и ограничения: [docs/ml-price-estimation.md](docs/ml-price-estimation.md).
